# def_manager

## Платформа автоматизации юридических процессов

Платформа для автоматизации работы юристов по банкротству. Система объединяет сбор информации из государственных информационных систем, обработку судебных дел, генерацию документов и управление пользовательскими запросами.

Основная задача проекта — сократить количество ручных операций при работе с судебными делами и автоматизировать получение актуальной информации из внешних источников.

### Основные возможности

#### 1. Автоматический сбор данных

Реализованы два независимых парсера для работы с внешними информационными системами:

Картотека арбитражных дел (kad.arbitr.ru) — получение информации о судебных делах, документах и датах судебных заседаний.

ЕФРСБ (old.bankrot.fedresurs.ru) — получение информации об арбитражных управляющих, включая ИНН и сведения о СРО.

Для работы с источниками используются Playwright и Patchright. Инструменты разделены с учетом особенностей взаимодействия с каждым ресурсом.

#### 2. Асинхронная обработка задач

Длительные операции парсинга вынесены из основного приложения в фоновые задачи Celery.

Реализованы следующие сценарии:

При регистрации пользователя автоматически запускается сбор информации из ЕФРСБ.

При добавлении судебного дела запускается задача получения информации из Картотеки арбитражных дел.

После завершения парсинга полученные данные сохраняются в PostgreSQL и становятся доступны в пользовательском интерфейсе.

Ориентировочное время получения данных:

Информация об арбитражном управляющем — 10–15 секунд.

Информация о судебном деле — 15–20 секунд.

Таким образом, пользователь может продолжать работу с платформой, пока данные собираются в фоновом режиме.

### 3. Изолированная инфраструктура парсеров

Каждый парсер вынесен в отдельный Docker-контейнер.

Такое разделение позволяет:

Использовать независимые наборы библиотек и их версий.

Исключить конфликты зависимостей между инструментами автоматизации браузера.

Независимо управлять выполнением задач для разных источников.

Настраивать обработку и расписание парсинга отдельно для каждого ресурса.

Для каждого источника предусмотрена собственная очередь Celery и последовательная обработка задач с одним worker.

### 4. Контроль нагрузки на внешние ресурсы

При реализации парсеров учитывались ограничения внешних информационных систем.

Реализованы:

Последовательная обработка задач в очередях.

Задержки между обращениями к внешним ресурсам.

Контроль интенсивности запросов.

Плановый ночной сбор данных с использованием шедулера.

Это позволяет управлять частотой обращений и снижать риск блокировки доступа к источникам.

### 5. Генерация документов

Реализована автоматическая генерация документов Word для подготовки запросов в государственные органы.

Документы формируются на основе заранее подготовленных шаблонов с подстановкой необходимых данных.

Используется библиотека python-docx.

### 6. Пользовательская система

Реализованы:

Регистрация пользователей.

Подтверждение email с помощью кода верификации.

Работа с судебными делами.

Управление запросами.

Отображение информации, полученной из внешних источников.

### Принципы организации фоновой обработки

Celery использует синхронные задачи, внутри которых запускаются асинхронные функции парсеров через asyncio.run().

Для каждого парсера используется собственный контейнер и отдельный worker. Асинхронный API Playwright/Patchright позволяет выполнять операции ввода-вывода без блокировки event loop парсера.

Изоляция фоновых процессов от FastAPI позволяет не блокировать обработку пользовательских HTTP-запросов во время выполнения длительных операций.

### Технические решения

В проекте особое внимание уделено разделению пользовательской логики и фоновых процессов.

Основные архитектурные решения:

Изоляция парсеров в отдельных Docker-контейнерах для независимого управления зависимостями.

Разделение очередей фоновых задач по внешним источникам.

Последовательная обработка задач каждого парсера с учетом ограничений внешних ресурсов.

Использование асинхронного API браузерной автоматизации внутри Celery workers.

Сохранение результатов парсинга в PostgreSQL для последующего отображения в пользовательском интерфейсе.

Плановое выполнение фонового сбора данных.
## Слои

- **Repositories** — только SQLAlchemy: `select`, `joinedload`, `selectinload`.
- **Services** — сценарии: проверка прав, создание связанных сущностей, генерация документов.
- **Routers** — HTTP: принять форму, вызвать сервис, отрендерить шаблон или вернуть JSON.
- **Schemas** — валидация входных данных через Pydantic. ORM-модели в шаблон отдаются напрямую, без промежуточного слоя.
